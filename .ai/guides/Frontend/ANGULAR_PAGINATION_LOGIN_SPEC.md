# Angular Pagination and Login Integration Specification

## Purpose and source of truth

This document describes the backend contract that the Angular application must consume for pagination and basic access control. It is based on backend commits:

- `c50f60c` — `APP-0007: Cache and pagination added`
- `4e4822e` — `APP-0008: Profiles, cache and basic security implementation`

The contracts below reflect the current Java implementation. Known backend limitations are called out explicitly and must not be interpreted as already fixed.

The examples assume a local API base URL of `http://localhost:8080`.

## Authentication contract

### Login endpoint

```http
POST /api/login
```

This is the only `/api/**` endpoint excluded from the API-key interceptor. It does not require an `Authorization` header.

#### Request parameters

The controller accepts credentials as request parameters, not as a JSON request body.

| Parameter | Type | Required in practice | Description |
| --- | --- | --- | --- |
| `username` | string | Yes | Username stored by the backend |
| `password` | string | Yes | Plain-text password submitted for comparison |

The safest client contract is to send both values as URL-encoded query parameters:

```http
POST /api/login?username=demo%40example.com&password=my%20password
```

```bash
curl -X POST "http://localhost:8080/api/login?username=demo%40example.com&password=my%20password"
```

Do not send this payload unless the backend controller is changed to accept a request body:

```json
{
  "username": "demo@example.com",
  "password": "my password"
}
```

#### Successful response

Status: `200 OK`

```json
{
  "apiKey": "configured-backend-api-key"
}
```

```ts
export interface LoginResponse {
  apiKey: string;
}
```

#### Invalid credentials

The service throws `UnauthorizedException("Credential errors")` when the username does not exist or the password does not match. The intended status is `401 Unauthorized` with an error payload similar to:

```json
{
  "error": "Credential errors"
}
```

However, this is not currently a reliable wire contract. See [Known backend limitations](#known-backend-limitations).

### Authenticated API requests

Every endpoint matching `/api/**`, except `/api/login`, requires this exact header:

```http
Authorization: Basic <apiKey>
```

Example:

```http
Authorization: Basic configured-backend-api-key
```

This is a custom API-key scheme. It is **not standard HTTP Basic Authentication**: do not Base64-encode `username:password`, and do not send a JWT or a `Bearer` token. The string returned in `LoginResponse.apiKey` must be appended directly after `Basic `.

If the header is absent, does not start with `Basic `, or contains the wrong key, the interceptor returns:

- Status: `401 Unauthorized`
- Header: `WWW-Authenticate: Basic realm="cheeseandcream"`
- Body: generated by the servlet/Spring error handling and therefore not a stable application payload

CORS currently permits the `Authorization`, `Cache-Control`, and `Content-Type` request headers. Preflight `OPTIONS` requests are excluded from authentication.

## Pagination contract

The following endpoints now accept Spring Data pagination parameters and return a serialized `Page` rather than a plain array.

| Resource | Endpoint | Content type |
| --- | --- | --- |
| Active agents | `GET /api/agents` | `AgentResponse[]` in `content` |
| Active products owned by an agent | `GET /api/products/agent/{agentId}` | `ProductResponse[]` in `content` |
| Active financial operations for an agent | `GET /api/financial-operations/agent/{idAgent}` | `FinancialOperationResponse[]` in `content` |

All three endpoints require the API-key header.

### Query parameters

| Parameter | Type | Default | Notes |
| --- | --- | --- | --- |
| `page` | non-negative integer | `0` | Zero-based page index |
| `size` | positive integer | `20` | Number of requested records per page |
| `sort` | string | unsorted | Format: `property,direction`; direction is `asc` or `desc` |

Multiple sort values may be sent by repeating the parameter:

```http
GET /api/agents?page=0&size=10&sort=name,asc&sort=id,asc
```

Use a valid entity property for sorting. The backend does not define a default sort, so the frontend should request an explicit stable sort when record order matters. Adding `id` as the final sort key avoids ambiguous ordering when the primary field contains duplicates.

Angular Material's `MatPaginator` already uses zero-based `pageIndex`. If a different UI component displays pages starting at 1, send `uiPage - 1` to the backend and display `response.number + 1` to the user.

### Page response envelope

The current services return Spring Data `Page<T>` instances. A representative direct serialization is:

```json
{
  "content": [],
  "pageable": {
    "pageNumber": 0,
    "pageSize": 20,
    "sort": {
      "empty": true,
      "sorted": false,
      "unsorted": true
    },
    "offset": 0,
    "paged": true,
    "unpaged": false
  },
  "last": true,
  "totalPages": 0,
  "totalElements": 0,
  "size": 20,
  "number": 0,
  "sort": {
    "empty": true,
    "sorted": false,
    "unsorted": true
  },
  "first": true,
  "numberOfElements": 0,
  "empty": true
}
```

The frontend only needs the stable fields below. Keeping the adapter narrow reduces coupling to Spring Data's additional serialization metadata.

```ts
export interface PageResponse<T> {
  content: T[];
  totalElements: number;
  totalPages: number;
  size: number;
  number: number;
  numberOfElements: number;
  first: boolean;
  last: boolean;
  empty: boolean;
}

export interface PageRequest {
  page: number;
  size: number;
  sort?: string[];
}
```

Treat `number` as the returned zero-based page index. Use `totalElements` as the paginator length and `size` as its page size. Do not calculate the total record count from `content.length`.

## Paginated endpoint specifications

### Get active agents

```http
GET /api/agents?page=0&size=10&sort=name,asc&sort=id,asc
Authorization: Basic <apiKey>
```

Successful status: `200 OK`

Only active agents are included.

### Get active products by agent

```http
GET /api/products/agent/15?page=0&size=10&sort=name,asc&sort=id,asc
Authorization: Basic <apiKey>
```

Path parameter:

| Parameter | Type | Description |
| --- | --- | --- |
| `agentId` | integer (`Long`) | Owner agent identifier |

Successful status: `200 OK`

Only active products associated with the supplied agent ID are included.

```ts
export interface ProductResponse {
  id: number;
  name: string;
  quantity: number;
  price: number;
  cost: number;
  unitType: string;
  categoryName: string;
  agentName: string;
}

export type ProductPage = PageResponse<ProductResponse>;
```

An unknown agent ID is not explicitly validated by this endpoint; the repository query can therefore return `200 OK` with an empty page.

### Get active financial operations by agent

```http
GET /api/financial-operations/agent/15?page=0&size=10&sort=creationDate,desc&sort=id,desc
Authorization: Basic <apiKey>
```

Path parameter:

| Parameter | Type | Description |
| --- | --- | --- |
| `idAgent` | integer (`Long`) | Agent identifier |

Successful status: `200 OK`

Only active operations associated with the supplied agent ID are included.

```ts
export type FinancialOperationType =
  | 'SALE'
  | 'PURCHASE'
  | 'PAYMENT'
  | 'CLIENT_PAYMENT';

export interface FinancialOperationProductResponse {
  id: number;
  name: string;
  quantity: number;
  totalPrice: number;
}

export interface FinancialOperationResponse {
  id: number;
  productResponses: FinancialOperationProductResponse[];
  idAgent: number;
  concept: string;
  total: number;
  operationType: FinancialOperationType;
  date: string | null;
}

export type FinancialOperationPage = PageResponse<FinancialOperationResponse>;
```

`date` is formatted as an ISO local date-time without a timezone, for example `2026-09-10T14:30:00`. Do not treat it as UTC unless the backend contract is changed to include an offset or zone.

As with products, an unknown agent ID can produce `200 OK` with an empty page rather than `404 Not Found`.

## Recommended Angular integration

### Centralized page request builder

Keep pagination parameters in one helper so every data service follows the same zero-based convention.

```ts
import { HttpParams } from '@angular/common/http';

export function toPageParams(request: PageRequest): HttpParams {
  let params = new HttpParams()
    .set('page', request.page)
    .set('size', request.size);

  for (const sort of request.sort ?? []) {
    params = params.append('sort', sort);
  }

  return params;
}
```

Each Angular API service should request `PageResponse<T>`, then expose only the fields needed by components. Replace the displayed collection with `response.content` after every successful request.

Pagination behavior:

1. Initialize with `page = 0` and the UI's chosen page size.
2. On a paginator event, request the emitted zero-based page index and page size.
3. When a filter, search term, agent selection, or page size changes, reset `page` to `0` before loading.
4. Set the paginator length from `totalElements`.
5. Disable previous/next controls from `first` and `last`, or from the equivalent paginator state.
6. Preserve a stable explicit sort across page changes.
7. If a delete makes the current nonzero page empty, request the preceding page once.

### Login service

```ts
import { HttpClient, HttpParams } from '@angular/common/http';
import { Injectable } from '@angular/core';
import { Observable, tap } from 'rxjs';

const API_KEY_STORAGE_KEY = 'cheeseandcream.apiKey';

@Injectable({ providedIn: 'root' })
export class AuthService {
  constructor(private readonly http: HttpClient) {}

  login(apiUrl: string, username: string, password: string): Observable<LoginResponse> {
    const params = new HttpParams()
      .set('username', username)
      .set('password', password);

    return this.http
      .post<LoginResponse>(`${apiUrl}/api/login`, null, { params })
      .pipe(tap(({ apiKey }) => sessionStorage.setItem(API_KEY_STORAGE_KEY, apiKey)));
  }

  getApiKey(): string | null {
    return sessionStorage.getItem(API_KEY_STORAGE_KEY);
  }

  isAuthenticated(): boolean {
    return this.getApiKey() !== null;
  }

  logout(): void {
    sessionStorage.removeItem(API_KEY_STORAGE_KEY);
  }
}
```

The login page should:

- Require both fields before submission.
- Disable repeated submission while the request is pending.
- Avoid logging credentials or the returned API key.
- Store the key only after a successful response.
- Navigate to the application's authenticated landing page after success.
- Show a generic invalid-credentials message for the intended 401 response.
- Show a temporary server-error message for unexpected 5xx responses, including the current invalid-credentials defect.

### Authorization interceptor

The interceptor must append the API key exactly as the backend expects:

```ts
export const authInterceptor: HttpInterceptorFn = (request, next) => {
  const apiKey = sessionStorage.getItem('cheeseandcream.apiKey');

  const authenticatedRequest = apiKey
    ? request.clone({
        setHeaders: { Authorization: `Basic ${apiKey}` },
      })
    : request;

  return next(authenticatedRequest);
};
```

Add centralized 401 handling to clear `cheeseandcream.apiKey` and redirect to the login route. Avoid redirect loops when the failed request is `/api/login`; that request should leave the user on the login page and display its validation error.

Do not manually set `Access-Control-Allow-*` headers in Angular. Those are response headers controlled by the backend.

### Route access and logout

- A route guard should allow protected routes only when the session API key exists.
- The guard is a client-side navigation convenience, not proof that the API key is valid; the backend remains authoritative.
- Logout should remove the stored key and navigate to the login page.
- Because `sessionStorage` is used, closing the browser tab ends the local session.

## Known backend limitations

These are observations about the current code and are not part of the frontend implementation:

1. `UnauthorizedExceptionAdvice.handleNotFoundException` has `@ResponseStatus` but no `@ExceptionHandler(UnauthorizedException.class)`. Invalid credentials may therefore be handled as an unhandled exception and return `500 Internal Server Error` instead of the intended `401 Unauthorized` JSON response.
2. User passwords are Base64-encoded, not securely password-hashed. Base64 is reversible and must not be treated as password protection.
3. The returned API key is a shared static configuration value, not a user-specific or expiring session token.
4. The custom `Basic <apiKey>` header is not standards-compliant Basic Authentication despite using the `Basic` scheme name.
5. Direct serialization of Spring Data `Page` is framework-dependent. Keep the raw envelope behind a frontend adapter and rely only on the fields in `PageResponse<T>`.
6. The cached agents query uses only page number and page size as its cache key. Different sort orders for the same page and size can receive a previously cached order until that cache is evicted.
7. No deterministic default sorting is configured. Always send an explicit sort for user-visible pagination.
8. Missing login parameters do not have an explicitly documented validation response and may result in an unexpected server error. The Angular form must prevent empty submissions.

The `/api/users` creation, update, and deletion endpoints are also protected by the API-key interceptor, but their UI and contracts are outside this document's scope.

## Acceptance scenarios for the Angular implementation

### Pagination

- The first request sends `page=0`, displays `content`, and uses `totalElements` as the paginator length.
- Moving to the second visible page sends `page=1`, not `page=2`.
- Changing page size resets the request to `page=0`.
- Changing a filter, search term, or selected agent resets the request to `page=0`.
- An empty first page renders a valid empty state without treating it as an error.
- `last: true` prevents requesting a later page through normal navigation.
- Sorting persists while moving between pages and includes a deterministic tie-breaker such as `id`.
- If deletion empties a nonzero page, the UI loads the preceding page once.

### Authentication

- Valid credentials call `POST /api/login` with URL-encoded request parameters and no JSON body.
- A successful login stores `apiKey` in `sessionStorage` and navigates to the authenticated area.
- Subsequent protected requests contain exactly `Authorization: Basic <apiKey>`.
- The login request works without an existing API key.
- Intended invalid-credential responses show a generic message without storing a key.
- Unexpected 5xx responses from invalid credentials show a recoverable server-error state because of the known backend exception-handler defect.
- A protected request made without a key is rejected with 401 and redirects to login.
- A protected request made with an incorrect key is rejected with 401, clears the stored key, and redirects to login.
- Logout removes the key and prevents guarded navigation until another successful login.
